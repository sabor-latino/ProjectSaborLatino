# Coordinación de agentes — ProjectSaborLatino

Este archivo contiene las reglas permanentes. El intercambio operativo entre Codex (orquestador y revisor) y Gemini 4 Argon (implementador en la terminal de Antigravity CLI, comando `agy`) ocurre exclusivamente en `COMUNICACION_CODEX_GEMINI.md`, en esta misma carpeta (bitácora operativa local no versionada en Git, excluida mediante `.git/info/exclude`). No usar el chat del IDE como canal de trabajo. Ambos deben leer `AGENTS.md` y `COMUNICACION_CODEX_GEMINI.md` (cuando exista en el entorno local) **al iniciar cada tarea y antes de responder**, y respetar las guías de `CONTRIBUTING.md`. El usuario define objetivos y tiene la decisión final. Las instrucciones del usuario y las de mayor prioridad prevalecen.

## Reglas de trabajo

1. **Lectura previa y órdenes explícitas:** Codex escribe una orden concreta en `COMUNICACION_CODEX_GEMINI.md`: identificador, alcance, archivos autorizados, criterios de aceptación y verificaciones. Gemini no infiere una orden a partir de un comentario informal. Si falta información imprescindible, lo informa en ese archivo y en su terminal.
2. **Acuse y alcance estricto:** Gemini confirma la orden con `ACEPTADA` y el `HEAD` y estado de Git observados antes de editar. Trabaja solo en el alcance autorizado. Codex no edita los mismos archivos mientras Gemini los trabaja. Un solo agente escribe el archivo de comunicación a la vez; cada intervención se agrega al final, sin borrar entradas anteriores.
3. **Preservación de cambios ajenos:** Nadie sobrescribe, revierte, mueve, confirma ni publica cambios ajenos o preexistentes del usuario. Antes y después de cada tarea se ejecuta `git status --short` (o `git status --short --untracked-files=all`) y se distingue lo preexistente de lo propio. No se hace `git pull`, `reset`, `clean`, `push`, merge, migración de base de datos personal ni borrado de datos sin una orden que lo autorice expresamente.
4. **Verificación real obligatoria antes de entregar:** Todo cambio de comportamiento requiere una comprobación automatizada capaz de fallar si el cambio está roto (evidencia roja previa cuando se corrige un defecto, seguida de prueba verde). Se ejecutan, según corresponda, compilación, análisis de vulnerabilidades, pruebas automatizadas y una prueba de ejecución real. No se declara `VERIFICADO` ni `ENTREGADA` por haber leído el código o porque solo compiló. Si falta infraestructura, se marca `BLOQUEADO`, con el error exacto y la verificación pendiente.
5. **Entrega transparente y revisión independiente:** Gemini entrega en el archivo de comunicación y en su terminal: resumen, archivos modificados, comandos ejecutados, resultado y código de salida, pruebas, riesgos, problemas preexistentes y `git diff --check`. No oculta advertencias ni maquilla límites de verificación. Codex revisa el diff y repite las pruebas críticas por cuenta propia en corrección, claridad, arquitectura, seguridad y rendimiento; puede devolver `CAMBIOS REQUERIDOS`. Solo Codex marca `APROBADA` después de revisar.
6. **Base aislada, API, frontend y dependencias:**
   - **Base de datos y pruebas de backend:** toda prueba automatizada usa una base temporal aislada con nombre único (`SaborLatinoDb_Test_<GuidN>`) sobre SQL Server LocalDB, aplica las migraciones reales de EF Core y elimina únicamente esa base temporal en `DisposeAsync`/`finally`. Jamás usar ni mutar la base personal `SaborLatinoDb`.
   - **API y autorización:** probar respuestas esperadas (`200`/`201`/`204`), rechazos de autenticación/autorización (`401`/`403`), aislamiento entre usuarios (`404`) y persistencia en base de datos.
   - **Frontend en CI vs propiedad del código:** en CI (`.github/workflows/ci.yml` + `.github/scripts/verify-frontend-ci.mjs`) se exige para todo paquete bajo `frontendSL/` (raíz o anidado) contar con lockfile (`package-lock.json` o `npm-shrinkwrap.json`) e instalar con `npm ci`, ejecutar `npm run lint`, `npm run build` y cumplir el contrato `test:ci` para que cualquier suite futura se ejecute automáticamente sin enumerar archivos ni carpetas en el workflow. No afirmar que `lint` o `build` prueban interacción en navegador o apariencia visual, ni que exista ya una suite de pruebas de frontend mientras no se haya agregado.
   - **Dependencias:** registrar la versión afectada y aplicar una solución acotada y probada; no ejecutar actualizaciones masivas a ciegas.
7. **Prohibición de secretos:** No se escriben secretos, contraseñas, tokens, claves privadas ni volcados de base en este archivo, en `COMUNICACION_CODEX_GEMINI.md`, en código, en logs ni en Git. Cada tarea produce cambios pequeños y revisables. Ante un fallo, detener la entrega y reportarlo; nunca maquillar el estado como éxito.
8. **Prohibido modificar `frontendSL/` o integrar PR que lo modifiquen:** Esa carpeta y sus PR (#10, #11 y sucesivos) pertenecen a otra persona. En el árbol compartido, Codex y Gemini pueden leer contratos y ejecutar verificaciones sin modificar archivos de código ni dependencias; no editan, formatean, actualizan dependencias, hacen checkout que sustituya archivos ni fusionan ramas ajenas. El job de CI del frontend corre en un runner desechable y puede instalar dependencias y generar artefactos temporales allí para ejecutar `lint`, `build` y `test:ci`. El veto sobre cambios al código del frontend prevalece sobre las recomendaciones generales de este archivo.

## Puertas de CI y publicación

- El workflow `.github/workflows/ci.yml` se ejecuta en `push` y `pull_request` sin filtros de rutas y con token de solo lectura (`contents: read`), validando tanto el job de backend (`windows-2022` + LocalDB + `dotnet test`) como el de frontend (`ubuntu-latest` + `node .github/scripts/verify-frontend-ci.mjs`).
- Ningún paso de CI puede ocultar fallos con `continue-on-error`.
- Para que GitHub bloquee técnicamente la fusión de PRs cuando falle alguna puerta, se debe configurar en GitHub la protección de la rama `main` (*Branch protection rules* / *Rulesets* con *Require status checks to pass before merging*) una vez publicado el workflow y ejecutada su primera corrida, tal como se documenta en `CONTRIBUTING.md`.
